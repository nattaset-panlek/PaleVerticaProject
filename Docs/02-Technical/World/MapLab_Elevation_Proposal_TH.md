# MapLab Elevation Proposal (TH): เดินขึ้นลง Plateau

ข้อเสนอแนวคิดให้ตัวละครเดินขึ้นไปบน Plateau เดินลงทางลาด/บันได และกระโดดลงจากขอบได้ โดย **ไม่กระทบเกม 2D ที่อ่านไฟล์ walkable อยู่แล้ว** และใช้ได้ไม่ว่าผู้ซื้อ MapLab จะทำเกมแบบไหน (grid A*, NavMesh, Rigidbody2D, tile)

- สถานะ: **concept ยังไม่ได้สร้าง** รอผู้ใช้อ่านและตอบคำถามในหัวข้อ 15
- วันที่: 2026-10-24
- เกี่ยวข้อง: [Extruded_Shape_Walkthrough_TH.md](./Extruded_Shape_Walkthrough_TH.md), [Walkable_Area_Bake_Walkthrough_TH.md](./Walkable_Area_Bake_Walkthrough_TH.md), [MapLab_Bake_Layers_Walkthrough_TH.md](./MapLab_Bake_Layers_Walkthrough_TH.md), [Walkable_Grid_Pathfinding_Walkthrough_TH.md](./Walkable_Grid_Pathfinding_Walkthrough_TH.md)

## สรุปสั้น

- ตำแหน่งจริงของตัวละครอยู่บน **ระนาบพื้น (footprint)** เสมอ ความสูงเป็นแค่ตัวเลขที่ใช้ยกภาพขึ้น
- MapLab bake **แผนที่ความสูง** (ช่องไหนเป็นชั้นไหน ช่องไหนเป็นทางลาด) ลงไฟล์ใหม่แยกจาก `Walkable.json` เกมเดิมจึงไม่เห็นอะไรเปลี่ยน
- ตัวละครรู้ว่ากำลังขึ้น Plateau โดย **ถามแผนที่ว่าใต้เท้าคืออะไร** ทุกครั้งที่ขยับ ไม่ต้องใช้ trigger
- เรื่องยากมีสามเรื่อง: **Sort Y** (หัวข้อ 9), **Collision** (หัวข้อ 10), **Bake** (หัวข้อ 11) ทั้งสามแก้ได้ด้วยข้อมูลชุดเดียวกันและ API เดียว (หัวข้อ 8)

## 1. สิ่งที่มีอยู่ตอนนี้ (อ่านจากโค้ด)

| เรื่อง | ตอนนี้ | ที่มา |
|---|---|---|
| footprint | จุดของ shape = รอยบนพื้น = collider | `ExtrudedShape.BuildCollision` |
| ความสูง | หลังคาวาดที่ footprint + (0, BaseElevation + Height) คือ **เลื่อนภาพขึ้นในแกน Y อย่างเดียว** ตำแหน่งบนพื้นไม่เปลี่ยน | `ShapeMeshData.cs:57-60, 88` |
| tier | shape ลูกยืนบนหลังคาพ่อ `BaseElevation = พ่อ.TopElevation` ไม่มี collider | `ExtrudedShape.BaseElevation`, `IsStacked` |
| walkable | ทั้ง footprint เป็นสิ่งกีดขวาง เดินขึ้นไม่ได้ | `MapLabWalkableBaker` (Physics2D.OverlapBox) |
| การเรียงภาพ | ตัด slice ตาม y ของ footprint หลังคาแต่ละ slice เรียงที่ **ขอบใต้** ของมัน | `ExtrudedShape.cs:220` |
| ภาพที่ bake | sorted layer bake กำแพงและหลังคาเป็นชิ้นๆ พร้อมจุดเรียงของแต่ละชิ้น | `MapLabSortedBaker` |
| ผู้อ่านในเกม | `WalkableGridLoader` รับเฉพาะ `version == 1` อย่างอื่นปฏิเสธ | `WalkableGridLoader.cs:75` |

ข้อสรุป: MapLab คิดแบบ **"พื้นราบ + ความสูง"** อยู่แล้ว (tier ก็ใช้วิธีนี้) แค่ยังไม่ส่งความสูงออกไปให้คนอื่นใช้

## 2. แนวคิดหลัก: ตำแหน่งอยู่บนพื้นเสมอ ความสูงเป็นแค่ตัวเลขเพิ่ม

```
ภาพที่เห็น (visual)                    ตำแหน่งจริง (logical) = ระนาบ footprint

   +-----------+  <- หลังคา (y + 1.5)      +-----------+
   |  @        |     ตัวละครวาดที่นี่       |  @        |  <- root ของตัวละครอยู่ตรงนี้ (x, y)
   +-----------+                          |           |     level 1, h = 1.5
   |  กำแพง    |                          +-----------+
   +-----------+  <- footprint                  |#|  <- ทางลาด h ไล่ 0 -> 1.5
        |#|  ทางลาด                             
                                          พื้นรอบๆ = level 0, h = 0
```

1. **ทุกระบบของเกม (ตำแหน่ง ฟิสิกส์ AI ระยะโจมตี) ทำงานบนระนาบ footprint** เหมือนเกม 2D ทั่วไป
2. MapLab บอกเพิ่มแค่สองอย่าง: **ความสูงของพื้น** ณ จุดนั้น `h(x, y)` และ **ข้ามจากจุดหนึ่งไปอีกจุดได้ไหม** (ทางลาด ขอบหน้าผา กระโดดลง)
3. ภาพของตัวละคร = ตำแหน่ง + (0, h) ยกเฉพาะ child ที่เป็นภาพ ไม่ยก root
4. footprint ของ Plateau ไม่ซ้อนกันบนระนาบ (หลังคาของ Plateau คือ footprint ของมันเอง tier อยู่ข้างในพ่อ) ดังนั้น **หนึ่งจุดมีพื้นได้ชั้นเดียว** ใช้ height map ธรรมดาพอ
5. root ของตัวละครอยู่ที่ตำแหน่งจริง Unity เรียง SortingGroup ตามตำแหน่ง root จึงเรียงตาม y บนพื้นเหมือน shape อยู่แล้ว

### ทำไมไม่ให้เดินบนภาพตรงๆ (เลื่อน root ขึ้นไปบนหลังคาจริงๆ)

| | พื้นราบ + ความสูง (เสนอ) | เดินบนภาพ |
|---|---|---|
| พื้นที่ด้านหลัง Plateau | ไม่ทับกัน | หลังคาทับพื้นด้านหลังบนจอ จุดเดียวมีสองความหมาย |
| Physics2D | collider ของแต่ละชั้นอยู่ที่ footprint เดียวกัน สลับได้ง่าย | collider ของพื้นด้านหลังกับหลังคาซ้อนกัน |
| ระยะโจมตี / AI | ระยะจริงบนพื้น | ระยะบนจอบิดตามความสูง |
| เกมที่ไม่สนความสูง | ไม่ต้องแก้อะไร | ต้องแก้ |

## 3. หลัก "ไม่กระทบเกม": แยกไฟล์และให้เลือกใช้เอง

- **`Walkable.json` v1 ไม่เปลี่ยนแม้แต่ไบต์เดียว** Plateau และทางลาดยังเป็นสิ่งกีดขวาง (โลกแบบ "ปีนไม่ได้") เกมที่อ่าน v1 อยู่ (Pale Vertica, sample NavMesh) ทำงานเหมือนเดิม
- เพิ่มไฟล์ข้างกัน **`Walkable_Elevation.json`** (มี version ของตัวเอง) เขียนเมื่อแมพมี shape ที่เปิด Walk On Top หรือมีทางลาดเท่านั้น
- เกมที่อยากให้เดินขึ้นได้ **เลือกอ่านไฟล์นี้เอง** ไม่ต้องอ้างโค้ด MapLab
- ไม่ bump `Walkable.json` เป็น v2 เพราะ `WalkableGridLoader` จะปฏิเสธทันที และไม่ยัดฟิลด์เพิ่มใน v1 เพราะไฟล์ที่ทุกคนอ่านจะใหญ่ขึ้นและความหมายไม่ชัด
- ของใน Scene ที่ MapLab เพิ่ม (collider ของชั้นบน หัวข้อ 10) ปิดไว้เป็นค่าเริ่ม จึงไม่ไปชนกับตัวละครของเกมที่ไม่ได้เปิดใช้

## 4. ฝั่งสร้างแมพ (authoring)

| ของ | ทำอะไร | ค่าเริ่ม |
|---|---|---|
| **Walk On Top** (ช่องใหม่ใน ExtrudedShape) | หลังคาเดินได้ที่ความสูง TopElevation ขอบ footprint กลายเป็นหน้าผา | Plateau: เปิด, Ring: ปิด (เปิด = เดินบนสันกำแพง), Box: ปิด, Void: ปิดเสมอ |
| **Step Height** (ช่องใหม่ใน MapLabMap) | ต่างกันไม่เกินค่านี้ = ข้ามได้เองโดยไม่ต้องมีทางลาด (ขอบถนน ลานเตี้ย Flat) | 0.25 หน่วย |
| **Ramp Shape** (shape ใหม่) | สี่เหลี่ยม 4 จุด ปลายบน snap เข้าขอบ shape ความสูงไล่จากปลายล่างถึงปลายบน วาดเป็นทางลาดหรือบันได ใช้ได้ทุกด้าน | สไตล์ Ramp / Stairs |
| **Drop Edge** (ทำเครื่องหมายช่วงขอบ) | ลงได้ทางเดียว กระโดดลงจากหน้าผา | ปิด |
| ของบนหลังคา (หิน ต้นไม้ บ้าน) | เป็นลูกของ shape เหมือน tier ยืนบนหลังคาของพ่อ collider ของมันขวางเฉพาะชั้นนั้น | กติกาเดียวกับ tier |

กติกาที่ทำให้ "สร้างยังไงก็ได้":

- **tier** ได้ความสูงจาก shape ที่อยู่บนสุดของจุดนั้นเสมอ ขอบ tier เป็นหน้าผาระหว่างชั้น 1 กับ 2 ใส่ทางลาดระหว่าง tier ได้เหมือนกัน
- **shape พี่น้องที่ footprint ทับกัน** (ไม่ใช่พ่อลูก): ชั้นที่สูงกว่าชนะ และหน้า Walkable เตือน
- **ทางลาดที่แคบกว่า agent** หรือปลายบนไม่แตะขอบ shape: หน้า Walkable เตือน
- **สะพานหรือทางลอดใต้** (จุดเดียวมีสองพื้น) ไม่รองรับในรอบนี้ แต่รูปแบบไฟล์เผื่อไว้

### 4.1 ทางลาดจากโหมด Edit Points (ตามคำตอบข้อ 4, ออกแบบสำหรับ P2)

```
Edit Points ของ Plateau                  ทางลาดที่ได้ (ลูกของ Plateau)
  o-------o-------o                        o-------o--+=====+--o
  |               |   ชี้ขอบ -> [+ Ramp]    |          | ### |   |
  o------(+)------o                        o----------+=====+--o
                                                      |#####|  <- ลาดลงไปทางขอบที่ชี้
                                                      |#####|     จับลากได้: ตำแหน่งบนขอบ, ความกว้าง, ความยาว
                                                      +-----+
```

1. กด **Edit Points** ของ Plateau เมื่อเลื่อนเมาส์ไปบนขอบ (ไม่ใช่จุด) จะมีปุ่ม **+ Ramp** โผล่กลางช่วงนั้น
2. กดแล้วได้ **Ramp** เป็นลูกของ Plateau ปลายบนติดขอบตรงนั้น ทิศลาด = ออกจากขอบตามแนวตั้งฉาก
3. ค่าที่ปรับได้ (inspector และ handle ใน Scene view):

| ค่า | ความหมาย | handle |
|---|---|---|
| Position | ตำแหน่งบนเส้นรอบ footprint (0 ถึง 1) เลื่อนไปตามขอบได้ ข้ามมุมได้ | ลากจุดกลางปลายบนไปตามขอบ |
| Width | ความกว้างทางลาด | ลากขอบซ้าย/ขวา |
| Length | ความยาวแนวราบ = ลาดแค่ไหน (สั้น = ชัน) แสดงองศาให้ดู | ลากปลายล่าง |
| Angle | หมุนทิศลาดออกจากแนวตั้งฉาก (ทางลาดเฉียงเลียบหน้าผา) | ลากหัวลูกศร |
| Style | Ramp (ลาดเรียบ) / Stairs (จำนวนขั้น) | |
| Side Walls | ขอบกันตกสองข้างของทางลาด | |
| Texture / สี | เหมือน wall และ top ของ shape | |

4. ขอบโค้ง: ปลายบนของทางลาดเป็นเส้นตรงระหว่างสองจุดบนเส้นรอบ (ตาม Position ± Width/2) ช่วงขอบนั้นกลายเป็น **ช่องเปิด** ของหน้าผา ที่เหลือยังกันตกตามปกติ
5. ใช้ได้ทุกด้าน: ทางลาดด้านเหนือจะถูก Plateau บังบางส่วน (ถูกต้องตามมุมมอง) ทางลาดระหว่าง tier ก็ทำแบบเดียวกันจาก Edit Points ของ tier
6. แก้จุดของ Plateau แล้วทางลาดเลื่อนตาม เพราะเก็บเป็น Position บนเส้นรอบ ไม่ใช่พิกัด
7. ทำ preset ของทางลาดได้ (ค่า Width, Length, Style, Texture)
8. การเรียงภาพของตัวละครบนทางลาด: ทางลาดเป็น surface ที่ความสูงไล่จาก 0 ถึงความสูงของ Plateau ตัวละครบนทางลาดใช้ bias ของทางลาดเอง (ต้องเช็กด้วยตัวตรวจ Sort แบบเดียวกับ P0)

## 5. รูปแบบไฟล์ `Walkable_Elevation.json` (ร่าง version 1)

```json
{
  "version": 1,
  "walkable": "Walkable.json",
  "cellSize": 0.5, "columns": 100, "rows": 68,
  "stepHeight": 0.25,
  "levels": [
    { "id": 0, "height": 0.0, "sortBias": 0.0, "name": "Ground" },
    { "id": 1, "height": 1.5, "sortBias": 0.51, "name": "Plateau" },
    { "id": 2, "height": 2.5, "sortBias": 1.02, "name": "Plateau/Tier" }
  ],
  "cellLevel": "<base64, 1 ไบต์ต่อช่อง: เลข level, 254 = ทางลาด, 255 = เดินไม่ได้ทุกชั้น>",
  "ramps": [
    { "lower": 0, "upper": 1, "polygon": [ ... ], "bottom": [ {..}, {..} ], "top": [ {..}, {..} ] }
  ],
  "drops": [
    { "from": 1, "to": 0, "points": [ {..}, {..} ], "direction": { "x": 0, "y": -1 } }
  ],
  "cliffs": [ { "level": 1, "points": [ ... ], "openings": [ ... ] } ]
}
```

- **ที่สร้างจริงใน P1** (รายละเอียดใน [MapLab_Elevation_Walkthrough_TH.md](./MapLab_Elevation_Walkthrough_TH.md) หัวข้อ 3): `levels` มี `id`, `name`, `height`, `sortBias`, `below`; มี `bounds` ในไฟล์ด้วย; `cliffs` มี `level`, `inner`, `points` (ยังไม่มี `openings`); `ramps` มาใน P2 และ `drops` ภายหลัง โดยเพิ่มฟิลด์ใหม่ใน version 1 ได้เพราะผู้อ่านเก่าข้ามฟิลด์ที่ไม่รู้จัก
- กริดเดียวกับ `Walkable.json` ทุกช่อง จึงเอาไปซ้อนกันได้ตรงๆ
- **ความสูงที่จุดหนึ่ง** = `levels[cellLevel].height` หรือถ้าเป็นช่องทางลาด = ไล่ค่าจากเส้น `bottom` ไป `top` ของทางลาดนั้น
- **กติกาการเดินจาก A ไป B**: level เดียวกัน, หรือความสูงต่างไม่เกิน `stepHeight`, หรือผ่านช่องทางลาดที่เชื่อมสองชั้นนั้น, หรือข้าม drop edge ตามทิศ (ลงอย่างเดียว)
- `cliffs` คือเส้นขอบของแต่ละชั้น `openings` คือช่วงที่เว้นให้ทางลาดและ drop ใช้สร้าง collider หรือ NavMesh ของชั้นนั้น
- มี `Walkable_Elevation.png` (เทา = ความสูง) ไว้ดูด้วยตา
- อนาคต (สะพาน): เพิ่ม `layers[]` ที่แต่ละชั้นมีกริดของตัวเอง ใน version 2 ของไฟล์นี้

## 6. ฝั่งเกม: เลือกใช้ได้ 3 ระดับ

| ระดับ | เกมต้องทำ | ได้อะไร |
|---|---|---|
| 0 ไม่สนความสูง | ไม่ทำอะไร (Pale Vertica ตอนนี้) | Plateau เป็นกำแพงเหมือนเดิม |
| 1 เดินขึ้นลงได้ | ใส่ `ElevationBody` ที่ตัวละคร (หัวข้อ 8) หรือเขียนเองจากไฟล์: ถามชั้นใต้เท้า ยกภาพ เปลี่ยนจุดเรียง เปลี่ยน collision | ขึ้น Plateau ทางลาด กระโดดลง |
| 2 ใช้ความสูงในเกมเพลย์ | เกมตัดสินใจเอง เช่น ยิงจากที่สูงไกลขึ้น หน้าผาบังสายตา ตกแล้วเจ็บ AI ไม่ไล่ข้ามชั้น | MapLab ให้แค่ข้อมูลและ event ไม่บังคับกติกาเกม |

## 7. รู้ได้ยังไงว่ากำลังขึ้น Plateau

ไม่ต้องให้ Plateau "จับ" ตัวละคร ให้ตัวละคร **ถามแผนที่ความสูงว่าใต้เท้าคืออะไร** ทุกครั้งที่ขยับ

```
level 0           ทางลาด (254)                 level 1 (บน Plateau)
  @  -------->  [ bottom ===== กลาง ===== top ]  -------->  @
  h = 0          h ไล่ 0 ... 0.75 ... 1.5                  h = 1.5
                 OnRampEntered      สลับ collision       OnLevelChanged(0, 1)
                                    ที่เส้นกลาง
```

1. Bake รู้อยู่แล้วว่า footprint ไหนเปิด Walk On Top และทางลาดไหนติดขอบไหน จึงเขียนลงช่อง: ช่องนี้ level 1, ช่องนี้ทางลาดที่เชื่อม 0 กับ 1
2. ตอนตัวละครขยับ: เอาตำแหน่ง root ไปดูช่อง ถ้าเป็นทางลาด คำนวณว่าเดินไปกี่ส่วนจากเส้นล่างถึงเส้นบน ได้ความสูงไล่ไปเรื่อยๆ ภาพจึงค่อยๆ ลอยขึ้น
3. **level เป็นสถานะของตัวละคร ไม่ใช่แค่ตำแหน่ง**: เปลี่ยนเฉพาะตอนข้ามเส้นที่กำหนด (กลางทางลาด, เส้น drop) ไม่เปลี่ยนเพราะยืนชิดขอบ จึงไม่กะพริบไปมา และพร้อมสำหรับสะพานในอนาคต
4. ถ้าขยับไปช่องที่ข้ามไม่ได้ (เดินจากพื้นเข้าหน้าผา หรือเดินตกขอบที่ไม่ใช่ drop) จะถูกห้ามหรือไถลตามขอบ
5. Drop: ข้ามเส้น drop ตามทิศ = level ลด ความสูงของภาพตกลงตามเวลา (เกมใส่อนิเมชันกระโดดได้จาก event)

ไม่ใช้ trigger collider ที่ทางลาดเพราะ: ต้องมี physics, พลาดได้ถ้าเคลื่อนเร็วหรือ teleport, และ AI ที่หาเส้นทางล่วงหน้าต้องรู้ข้อมูลเดียวกันอยู่แล้ว

## 8. API

แบ่งเป็นสองชั้น ชั้นข้อมูลไม่มีสถานะ ใช้ได้ทั้ง AI และผู้เล่น ชั้นตัวละครถือสถานะและส่ง event

### 8.1 ชั้นข้อมูล: `ElevationMap` (อ่านจากไฟล์)

```csharp
ElevationMap map = ElevationMap.Load(elevationJson);

int    LevelAt(Vector2 ground);
float  HeightAt(Vector2 ground, int level);
bool   IsRamp(Vector2 ground, out RampInfo ramp);
bool   CanStep(Vector2 from, Vector2 to, int level);
Vector2 Constrain(Vector2 from, Vector2 to, int level, out int newLevel);
Vector2 ScreenToGround(Vector2 visualPoint, out int level);
float  SortBias(int level);
```

- `Constrain` คือหัวใจของ collision แบบไม่ใช้ physics: รับจุดเริ่มกับจุดที่อยากไป คืนจุดที่ไปได้จริง (ไถลตามขอบ) และ level ใหม่
- `ScreenToGround` ใช้กับคลิกเมาส์: ไล่ชั้นจากสูงไปต่ำ ลบความสูงของชั้นนั้นออกจาก y แล้วดูว่าช่องนั้นเป็นชั้นนั้นไหม
- AI หาเส้นทางด้วย `CanStep` เป็นเงื่อนไขเพื่อนบ้านของ A* ได้ทันที

### 8.2 ชั้นตัวละคร: `ElevationBody` (component บน root ของตัวละคร)

```
Character (root)            <- ตำแหน่งจริง, collider, Rigidbody2D, ElevationBody
  +- Sort Anchor            <- SortingGroup อยู่ที่นี่, y = -SortBias
       +- Visual            <- ภาพทั้งหมด, y = Height + SortBias
```

| สมาชิก | ทำอะไร |
|---|---|
| `Level`, `Height`, `IsOnRamp` | สถานะตอนนี้ |
| `Move(Vector2 delta)` | ขยับผ่าน `Constrain` แล้วอัปเดตสถานะ (เกมที่ขยับเองเรียก `Sync()` หลังขยับ) |
| `Teleport(Vector2 ground)` | วางตัวละครแล้วหา level จากจุดนั้น |
| `event OnLevelChanged(int from, int to)` | ขึ้นหรือลงชั้น |
| `event OnRampEntered / OnRampExited` | เข้า-ออกทางลาด (เล่นอนิเมชันเดินขึ้นบันได) |
| `event OnDropped(int from, int to)` | กระโดดลง |
| `event OnHeightChanged(float height)` | ความสูงเปลี่ยน (เงา ขนาดเงา) |
| Collision Mode | `Grid` (ใช้ `Constrain`), `Physics` (สลับ collider ตามชั้น หัวข้อ 10), `None` (เกมจัดการเอง) |

- `ElevationBody` ยก `Visual` และเลื่อน `Sort Anchor` เอง เกมแค่ subscribe event ถ้าอยากทำอะไรเพิ่ม
- ไม่ poll ใน `Update`: สถานะเปลี่ยนเฉพาะตอน `Move` / `Sync` / `Teleport`
- เป็นของใน MapLab Runtime ที่ **ไม่บังคับใช้** เกมที่ไม่อยากผูกกับ MapLab (เช่น Pale Vertica) เขียนตัวเองจากไฟล์ได้ตามหัวข้อ 5 และ 7

## 9. ปัญหา Sort Y

| กรณี | ผล | ต้องแก้ไหม |
|---|---|---|
| ตัวละครบนหลังคา กับกำแพงหน้า Plateau | กำแพง y ต่ำกว่า วาดหน้า แต่ภาพตัวละครยกพ้นกำแพงแล้ว ไม่ทับกัน | ไม่ |
| ตัวละครบนหลังคา กับต้นไม้บนพื้นด้านหลัง | ต้นไม้ y สูงกว่า วาดหลัง | ไม่ |
| ตัวละครบนพื้นด้านหลัง Plateau | ถูกหลังคาบังเหมือนเดิม `OccluderFadeController` ใช้ได้ | ไม่ |
| ตัวละครบนพื้นหน้า Plateau กับตัวละครบนหลังคา | ตัวบนพื้น y ต่ำกว่า วาดหน้า ถูกเพราะอยู่ใกล้กล้องกว่า | ไม่ |
| **ตัวละครบนหลังคา กับ slice ของหลังคาที่ตัวเองยืน** | slice เรียงที่ขอบใต้ (`ExtrudedShape.cs:220`) ตัวละครที่ยืนใน slice นั้น y สูงกว่า จึงถูกหลังคาวาดทับเท้า ได้มากสุดหนึ่ง slice (0.5 หน่วย) | **ต้องแก้** |

ทางแก้ (เลือกหลัง prototype):

- **(ก) ฝั่งตัวละคร: Sort Bias** ตัวละครที่อยู่ชั้นสูงกว่า 0 เลื่อน `Sort Anchor` ลง `SortBias(level)` (= `sortBias` ของชั้นในไฟล์ = `ExtrudedShape.SurfaceSortBias` = Sort Slice + 0.01 เท่ากับที่ Tier ของรูปนั้นใช้) แล้วยก `Visual` ขึ้นเท่ากันเพื่อให้ภาพอยู่ที่เดิม หลังคาไม่ต้องแก้ **เลือกแล้ว และผ่าน P0** (หัวข้อ 16)
- **(ข) ฝั่ง shape**: เมื่อเปิด Walk On Top ให้หลังคาเรียงที่ขอบเหนือของ slice แต่ตัวละครบนพื้นด้านหลังตรงขอบโค้งอาจโผล่ทับหลังคา ต้องลด slice ให้เล็กลง (ภาพแตกชิ้นมากขึ้น)

ถ้าใช้ (ก) ปัญหา Sort Y จึงกลายเป็น "API คืนค่า bias ให้" ตามที่ถาม เกมเรียก `SortBias(level)` หรือใช้ `ElevationBody` ที่ทำให้เอง

## 10. ปัญหา Collision

ตอนนี้ footprint ของ Plateau เป็น PolygonCollider2D ทึบ ถ้าตัวละครยืนบนหลังคา root อยู่ข้างใน polygon นี้ physics จะดันออก **ดังนั้น collision ต้องขึ้นกับชั้นของตัวละคร**

| ชั้นของตัวละคร | ต้องชนกับ | ต้องไม่ชนกับ |
|---|---|---|
| 0 (พื้น) | footprint ของ Plateau (เหมือนเดิม), ด้านข้างของทางลาด | ขอบหน้าผาของชั้นบน, ของบนหลังคา |
| 1 (บนหลังคา) | ขอบหน้าผาของ Plateau (เว้นช่องทางลาดและ drop), footprint ของ tier, ของบนหลังคา, ด้านข้างของทางลาด | footprint ของ Plateau ตัวเอง, ของบนพื้น |
| บนทางลาด | ด้านข้างของทางลาดเท่านั้น | footprint และขอบหน้าผา (สลับชุดที่เส้นกลางทางลาด) |

สามทางให้เลือกต่อตัวละคร (Collision Mode):

1. **Grid (เสนอเป็นค่าเริ่ม)**: ไม่ใช้ collider ของภูมิประเทศเลย ใช้ `Constrain` จากแผนที่ ใช้ได้กับทุกแบบเกม ไม่ต้องตั้ง Physics layer ตรงกับที่ AI ใช้หาเส้นทางเป๊ะ Pale Vertica มี `WalkableGrid` อยู่แล้วจึงเหมาะกับทางนี้
2. **Physics**: Walk On Top สร้าง child `Cliff` (EdgeCollider2D รอบ footprint เว้นช่อง) เพิ่มจาก `Collision` เดิม ทุก collider ที่ MapLab สร้างมีป้ายบอกชั้น ตอน level เปลี่ยน `ElevationBody` เรียก `Physics2D.IgnoreCollision(ตัวละคร, collider, true/false)` เป็นคู่ๆ **ไม่ต้องเพิ่ม Physics layer และไม่เปลี่ยน layer ของตัวละคร** เหมาะกับของที่ขาย เพราะไม่ไปแก้ Project Settings ของผู้ซื้อ (แมพใหญ่มากมีตัวเลือก layer ต่อชั้นแทน)
3. **None**: เกมทำเอง ใช้ `cliffs` ในไฟล์

ไม่ว่าจะทางไหน `Walkable.json` v1 ยังได้จาก footprint ทึบเหมือนเดิม

## 12. จุดอื่นที่ต้องระวัง

- **คลิกเมาส์บนหลังคา** ต้องผ่าน `ScreenToGround` ไม่อย่างนั้นคลิกบนหลังคาจะได้จุดบนพื้นด้านหลัง Plateau
- **เงาของตัวละคร** อยู่ที่ root (บนพื้นจริง) จะไปอยู่ใต้หลังคา ต้องให้เงาอยู่ใต้ `Visual` ที่ความสูงของพื้น ไม่ใช่ที่ root
- **ระยะโจมตีข้ามชั้น** ใช้ระยะบนพื้น ตัวบนหลังคากับตัวบนพื้นที่อยู่ติดหน้าผาจะตีกันได้ เกมต้องตัดสินใจเอง (ระดับ 2)

### Grid กับ Physics ต่างกันยังไง (ข้อ 3)

ทั้งสองแบบทำให้ "เดินตกขอบไม่ได้ และเดินจากพื้นทะลุเข้า Plateau ไม่ได้" เหมือนกัน ต่างกันที่ **ใครเป็นคนห้าม**

| | Grid | Physics |
|---|---|---|
| ใครห้าม | โค้ดดูแผนที่ช่องก่อนขยับ: ช่องข้างหน้าเดินจากชั้นนี้ได้ไหม ไม่ได้ก็ไถลตามขอบ | Unity Physics2D: มี collider เส้นขอบหน้าผาจริงในฉาก ตัวละคร (Rigidbody2D) ชนแล้วหยุดเอง |
| ตัวละครต้องมี | แค่ตำแหน่ง ขยับผ่าน `ElevationBody.Move` | Rigidbody2D + Collider2D และให้ physics เป็นคนขยับ |
| ขอบที่ได้ | หยาบตามขนาดช่อง (0.5 หน่วย) | ตรงตามรูปทรงเป๊ะ |
| ตรงกับ AI ไหม | ตรง 100% เพราะ A* ใช้แผนที่เดียวกัน | อาจต่างนิดหน่อย (AI เห็นเป็นช่อง ตัวละครชนเส้นจริง) |
| ชนกับของอื่น (ศัตรู กล่อง) | ไม่เกี่ยว ใช้ physics ของเกมต่อได้ตามเดิม | ใช้ physics เดียวกันหมด |
| เหมาะกับ | เกมคลิกเดิน, AI, เกมที่อยากได้ผลแน่นอน | เกม WASD ที่เคลื่อนด้วย physics อยู่แล้ว |

ใช้ร่วมกันได้: ตัวละครคนละ mode ในฉากเดียวกันได้ ข้อมูลมาจากไฟล์เดียวกัน

## 16. ผล P0 (2026-10-24)

วิธีรันและอ่านผล: [MapLab_Elevation_Walkthrough_TH.md](./MapLab_Elevation_Walkthrough_TH.md)

สิ่งที่สร้าง:

- `ExtrudedShape.WalkOnTop` (ค่าเริ่มปิด ฉากเดิมไม่เปลี่ยน): ด้านบนตัดแถบเสมอ ขั้นบนที่อยู่บนรูปนี้ก็ตัดแถบ (`ActorFloor` นับ Actor Height จากด้านบนที่มีคนยืน)
- `ExtrudedShape.SurfaceSortBias`: ค่าที่ Tier ของรูปนั้นเลื่อนอยู่แล้ว (Sort Slice + 0.01) ตอนนี้เป็นค่าเดียวกับที่ตัวละครบนด้านบนใช้ (`StackSortBias` ของ Tier อ่านจากค่านี้ ตัวเลขเท่าเดิม)
- ตัวตรวจ `MapLabElevationSortCheck`: เทียบลำดับวาดของ Unity กับความลึกจริงทีละจุดบนภาพ ใช้ซ้ำได้ใน P2 (ทางลาด) และ P3
- เทสต์ `ElevationSortTests` 6 ตัว ผ่าน, เทสต์ MapLab ทั้งหมด 108/108 ผ่าน (รวม `MapLabWindowStateTests` ที่แก้ให้ไม่วาด IMGUI นอก OnGUI)

ผล (ฉากชั่วคราว: Plateau 1.5 + Tier 1, ตัวละคร 9 ตัว ต้นไม้ 2 ต้น, 6,033 จุดตรวจ):

| แบบ | จุดผิด | สรุป |
|---|---|---|
| ไม่เลื่อน | 967 | ตัวละครบนที่สูงถูกทับทุกตัว |
| เลื่อนแค่พ้นแถบ (Snap) | 352 | ตัวละครที่ยืนหน้า Tier ถูกกำแพง Tier ทับ เพราะเลื่อนไม่เท่า Tier |
| **เลื่อนเท่า Tier (เลือก)** | 185 | ตัวละครไม่ถูกรูปทับเลย ที่เหลือคือตัวละครบนที่สูงวาดทับต้นไม้บนพื้นที่อยู่หน้าไม่เกิน 0.51 |
| เลื่อนเท่า Tier + Sort Slice 0.25 | 57 | เหลือต้นไม้ที่ห่างแค่ 0.2 (Plateau 17 -> 32 ชิ้น) |

ข้อสรุป:

1. กฎ: **ทุกอย่างที่ยืนบนด้านบน (ตัวละคร Tier ของบนหลังคา) เลื่อนจุดเรียงเท่ากัน = `sortBias` ของชั้นนั้น** จึงเรียงกันเองถูกเสมอ
2. ที่ยังผิดได้: ของสูงบนพื้นล่างที่อยู่หน้าตัวละครบนที่สูงไม่เกิน `sortBias` (เช่นต้นไม้ชิดหน้าผา) ลดได้ด้วย Sort Slice เล็กลง เสนอให้ Walk On Top ตั้ง Sort Slice 0.25 เป็นค่าแนะนำ (ตัดสินใจใน P1 พร้อมค่าเริ่มของ Walk On Top)
3. ไฟล์ elevation เก็บ `sortBias` ต่อชั้น (หัวข้อ 5) แทน `sortSlice` ตัวเดียว เพราะ Tier มี bias สะสม
4. ผลข้างเคียงที่รู้: Tier บนรูปที่ Walk On Top ไม่มีเงา (เงา Tier มีเฉพาะตอนรวมเป็นชิ้นเดียว) แก้ใน P1 ถ้าต้องการ
5. ยังไม่ได้ตรวจ: ภาพที่ bake ของ sorted layer กับ Walk On Top (ทาง (ก) ไม่เปลี่ยนจุดเรียงของชิ้น แต่จำนวนชิ้นเพิ่ม เพราะด้านบนตัดแถบ) และหน้าตาใน Unity editor จริง (ตรวจจากภาพ batch เท่านั้น)
