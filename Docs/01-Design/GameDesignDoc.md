เอกสารการออกแบบเกมและสถาปัตยกรรมเชิงระบบสำหรับเกม 2D RPG (Comprehensive Game Design Document & System Architecture)การพัฒนางานออกแบบสำหรับเกมแนวสวมบทบาท (Role-Playing Game หรือ RPG) ในรูปแบบ 2 มิติ (2D) ในยุคปัจจุบันจำเป็นต้องอาศัยการผสมผสานระหว่างความสุนทรีย์ที่กระตุ้นความทรงจำ (Nostalgia) และสถาปัตยกรรมเชิงระบบที่ลึกซึ้ง เอกสารการออกแบบเกม (Game Design Document หรือ GDD) ฉบับนี้ถูกจัดทำขึ้นเพื่อกำหนดทิศทางที่ชัดเจนและเป็นพิมพ์เขียว (Blueprint) ให้กับการพัฒนา โดยวิเคราะห์จากข้อมูลโครงสร้างพื้นฐานของระบบต้นแบบ ทั้งในด้านกลไกของตัวละคร การคำนวณค่าสถานะที่ซับซ้อน วงล้อการเล่น (Gameplay Loops) ไปจนถึงทิศทางศิลปะและประสบการณ์ผู้ใช้ (UX) เพื่อรองรับแนวโน้มของตลาดอุตสาหกรรมเกมในช่วงปี 2025-2026 เอกสารนี้จะทำหน้าที่เป็นกรอบการทำงานเชิงกลยุทธ์ที่ครอบคลุมทุกมิติ เพื่อให้มั่นใจว่าทุกฝ่ายในทีมพัฒนา ตั้งแต่นักออกแบบระบบ วิศวกรซอฟต์แวร์ ไปจนถึงศิลปิน สามารถทำงานภายใต้วิสัยทัศน์เดียวกัน โดยลดความเสี่ยงในการเกิดข้อผิดพลาดทางตรรกะในระบบที่มีความซับซ้อนสูง 1. วิสัยทัศน์และโครงสร้างพื้นฐานของโครงการ (Project Vision & Core Structure)ทิศทางของตลาดเกม 2D RPG ในช่วงปี 2025 นั้นให้ความสำคัญกับการยกระดับระบบการเล่นแบบดั้งเดิมด้วยกลไกทางคณิตศาสตร์ที่โปร่งใสและมีอิสระในการปรับแต่ง ผู้เล่นในยุคนี้มีความทนทานต่อระบบอินเทอร์เฟซที่ซับซ้อน หากระบบนั้นมอบผลตอบแทนทางยุทธวิธีที่คุ้มค่า  โครงการนี้จึงมุ่งเน้นไปที่การสร้างระบบการต่อสู้ที่ขับเคลื่อนด้วยข้อมูล (Data-driven combat system) และความยืดหยุ่นในการสร้างสายการเล่น (Build diversity) โดยหลีกเลี่ยงการจำกัดผู้เล่นไว้ในกรอบที่ตายตัวในแง่ของเอกสาร GDD ที่มีประสิทธิภาพ โครงสร้างจะถูกแบ่งออกเป็นส่วนของระบบที่เป็นกฎระเบียบ (Systems & Rules) เนื้อหา (Content) และการนำเสนอ (Presentation)  ระบบนิเวศของเกมนี้ถูกออกแบบมาให้หลอมรวมกลไกทุกอย่างเข้าด้วยกัน การกระทำใดๆ ของผู้เล่น ไม่ว่าจะเป็นการสวมใส่อุปกรณ์ การอัปเกรดทักษะ หรือการเดินทัพในโลกกว้าง จะต้องถูกคำนวณผ่านศูนย์กลางเดียวกันเพื่อความเสถียรของเกมเพลย์2. โครงสร้างเอนทิตีและกลไกพื้นฐาน (Core Entity System Mechanics)รากฐานที่สำคัญที่สุดของเกม RPG ที่มีระบบซับซ้อนคือการจัดการเอนทิตี (Entity Management) ภายในโลกของเกม สถาปัตยกรรมของเกมนี้ใช้โครงสร้างแบบลำดับชั้น (Hierarchical Structure) โดยกำหนดให้ตัวละครทุกตัว ไม่ว่าจะเป็นผู้เล่น (Player) หรือศัตรู (Enemy) ใช้ตรรกะทางโปรแกรมร่วมกันผ่านคลาสพื้นฐานที่เรียกว่า Base Character บทบาทของคลาส Base Characterการใช้คลาส Base Character เป็นศูนย์กลางช่วยให้กลไกทางฟิสิกส์และการคำนวณทั้งหมดมีความเป็นมาตรฐานเดียวกัน คลาสนี้มีหน้าที่จัดการรหัสประจำตัว (Unique IDs) ซึ่งจำเป็นอย่างยิ่งในการติดตามผลกระทบของสกิลและการบันทึกข้อมูล  นอกจากนี้ยังควบคุมระบบคุณลักษณะ (Attribute System) ระบบการเคลื่อนที่ (Movement System) และการฟื้นฟูทรัพยากร (HP/MP Recovery)  ความสำคัญของการออกแบบนี้คือ หากศัตรูมีค่าสถานะ Vitality (VIT) เท่ากับผู้เล่น ศัตรูตัวนั้นจะมีการฟื้นฟูพลังชีวิตและอัตราการทนทานต่อสถานะผิดปกติในระดับคณิตศาสตร์ที่เหมือนกันทุกประการ นอกจากกลไกเชิงตัวเลขแล้ว คลาสพื้นฐานยังรองรับระบบอวาตาร์และอุปกรณ์ โดยมีการแบ่งช่องใส่อุปกรณ์ (Equipment Slots) ออกเป็น 8 ช่องหลัก และช่องสำหรับชุดตกแต่ง (Costume Slots) อีก 4 ช่อง  การสร้างมาตรฐานโครงสร้างกระดูกและอุปกรณ์นี้ ช่วยให้ฝ่ายศิลป์สามารถออกแบบอาวุธหรือชุดเกราะเพียงชิ้นเดียว แต่นำไปสวมใส่ได้กับทั้งตัวละครผู้เล่นและ NPC ที่ใช้โมเดลพื้นฐานเดียวกันได้ทันทีความแตกต่างระหว่าง Player Character และ NPC/Enemyเมื่อขยายโครงสร้างออกมาเป็น Player Character ระบบจะทำการผูกมัด (Binding) เอนทิตีนี้เข้ากับระบบจัดการระดับโลก (Global Managers) เช่น ระบบสินค้าคงคลัง (Inventory) และระบบทักษะ (Skills)  เอนทิตีของผู้เล่นยังมีระบบตรวจสอบความก้าวหน้าผ่านต้นไม้ทักษะแบบพาสซีฟ (Passive Skill Tree) และมีเมนูสำหรับนักพัฒนา (Debug Menu) ที่ฝังอยู่ในระบบเพื่อใช้ทดสอบการเปลี่ยนแปลงค่าสถานะระหว่างการพัฒนาแบบเรียลไทม์ ในทางกลับกัน NPC/Enemy System จะถูกขยายคุณสมบัติด้วยโมดูลปัญญาประดิษฐ์ (AI) แทนที่การรับข้อมูลจากคอนโทรลเลอร์ของผู้เล่น ระบบ AI พื้นฐานรองรับคำสั่งเชิงพื้นที่ เช่น MoveTo (เคลื่อนที่ไปยังจุดหมาย) และ Follow (ติดตามเป้าหมาย)  สำหรับศัตรู จะมีตรรกะเฉพาะสำหรับการเผชิญหน้าในการต่อสู้ การเลือกเป้าหมาย และการรักษาระยะห่าง ซึ่งขับเคลื่อนด้วยค่าสถานะการเคลื่อนที่ที่เชื่อมโยงกับฟิสิกส์ในโลก 2D อย่างสมบูรณ์ 3. ระบบค่าสถานะและการคำนวณความก้าวหน้า (Attribute & Stat System Logic)หนึ่งในความท้าทายสูงสุดของการออกแบบ GDD สำหรับเกม RPG คือการสร้างระบบค่าสถานะที่ไม่ก่อให้เกิดสิ่งที่เรียกว่า "Dump Stats" หรือค่าสถานะที่ผู้เล่นมองข้ามและไม่ยอมอัปเกรดเลยเนื่องจากไม่มีประโยชน์ต่อรูปแบบการเล่นของตน  เพื่อแก้ไขปัญหานี้ สถาปัตยกรรมของเกมจึงออกแบบให้ค่าสถานะหลัก (Core Attributes) ทุกตัวมีความเชื่อมโยงและส่งผลลัพธ์ไปยังค่าสถานะการต่อสู้ (Combat Stats) ในหลากหลายมิติพร้อมๆ กัน คุณลักษณะหลักและการปรับขนาด (Core Attributes Scaling)ระบบพึ่งพาค่าสถานะหลัก 8 ประการในการกำหนดความสามารถของตัวละคร โดยแบ่งเป็นค่าสถานะประเภททรัพยากร 2 ประการ และค่าสถานะหลักที่ใช้คำนวณอีก 6 ประการ :HP (Hit Points): จุดตัดสินการรอดชีวิต คำนวณจาก $Base HP + Flat Bonus + (VIT \times 1\%)$ MP (Mana Points): ทรัพยากรหลักในการใช้ทักษะ คำนวณจาก $Base MP + Flat Bonus + (INT \times 1\%)$ STR (Strength): เพิ่มพลังโจมตีทางกายภาพ (Physical ATK) ในอัตราส่วน 1:1 และกำหนดขีดจำกัดน้ำหนัก (Weight Limit) ที่ตัวละครแบกได้ในอัตราส่วน 1:30 AGI (Agility): เพิ่มค่าการหลบหลีก (Flee) 1:1, เพิ่มความเร็วในการโจมตี (ASPD) 1:0.5 และเพิ่มพลังป้องกันสถานะผิดปกติ (Status DEF) 1:0.2 VIT (Vitality): หัวใจหลักของสายแทงค์ เพิ่ม Max HP 1:1%, เพิ่มการฟื้นฟู HP 1:0.2 และเป็นแกนหลักในการเพิ่ม Status DEF ถึง 1:0.7 INT (Intelligence): พลังแห่งเวทมนตร์ เพิ่มพลังโจมตีเวทมนตร์ (MATK) อย่างรุนแรงที่ 1:1.5, เพิ่ม Max MP 1:1%, การฟื้นฟู MP 1:0.16 และเพิ่ม Status DEF ที่ 1:1 DEX (Dexterity): ตัวกำหนดความแม่นยำ เพิ่มค่าความแม่นยำ (Hit) 1:1, เพิ่ม ASPD 1:0.15 และมีส่วนช่วยเพิ่มความเสถียรให้ทั้ง ATK และ MATK เล็กน้อยในอัตราส่วน 5:1 LUK (Luck): ค่าสถานะเหนือความคาดหมาย เพิ่มโอกาสคริติคอล (Crit Rate) 1:0.3, อัตราการหลบหลีกสมบูรณ์ (Perfect Dodge) 1:0.1 และเป็นแหล่งสร้างความเสียหายทางสถานะ (Status DMG) ตลอดจนให้โบนัสแฝงในค่าอื่นๆ อย่างละเล็กน้อย สมการตรรกะทางทหาร (Derived Combat Formulas)การใช้โครงสร้างสมการที่ซับซ้อนทำให้การสร้างตัวละครแบบผสมผสาน (Hybrid Builds) สามารถต่อสู้กับสายที่เน้นอัปสเตตัสเพียงด้านเดียวได้อย่างสูสี  ข้อมูลตารางด้านล่างแสดงให้เห็นถึงวิธีที่เอนจินของเกมจัดการกับคณิตศาสตร์เหล่านี้:ค่าสถานะการต่อสู้ (Combat Stat)สูตรการคำนวณ (Mathematical Formula)นัยสำคัญทางการออกแบบ (Design Implication)Physical ATK$STR + \frac{DEX}{5} + \frac{LUK}{3}$ความเสียหายทางกายภาพไม่ได้มาจากความแข็งแกร่ง (STR) เพียงอย่างเดียว แต่ต้องอาศัยความแม่นยำ (DEX) และโชค (LUK) ทำให้สายคริติคอลยังมีพลังโจมตีพื้นฐานที่ยอมรับได้ Magic ATK (MATK)$(INT \times 1.5) + \frac{DEX}{5} + \frac{LUK}{3}$ค่า INT มีตัวคูณถึง 1.5 ทำให้เวทมนตร์รุนแรงมาก แต่ยังคงใช้ DEX เพื่อความรวดเร็วและ LUK เพื่อโอกาสคริติคอลทางเวทมนตร์ Hit (Accuracy)$DEX + \frac{LUK}{3}$ตัวแปรสำคัญที่ใช้หักล้างค่า Flee ของศัตรู หากไม่มีค่า Hit ที่เพียงพอ พลังโจมตีที่สูงก็ไร้ความหมาย Critical Rate$LUK \times 0.3$ตรรกะที่อนุญาตให้ผู้เล่นโจมตีทะลุพลังป้องกันของเป้าหมายได้ พึ่งพา LUK เป็นหลัก Status DMG$(LUK \times 0.5) + \frac{INT}{4}$ความรุนแรงของการสร้างสถานะผิดปกติ (เช่น พิษ, เผาไหม้) ถูกขับเคลื่อนโดย LUK ทำให้สายควบคุมสถานะต้องพึ่งพา LUK อย่างมาก Status DEF$(VIT \times 0.7) + (AGI \times 0.2) + (LUK \times 0.2) + (DEX \times 0.2) + INT$ตรรกะที่สำคัญที่สุดที่ป้องกันไม่ให้เกิด Dump Stats เนื่องจากค่าหลักเกือบทุกตัวมีส่วนช่วยในการป้องกันสถานะผิดปกติ Flee (Evasion)$AGI + \frac{LUK}{5}$การหลบหลีกการโจมตีทางกายภาพอย่างสมบูรณ์ Perfect Dodge$\frac{LUK}{10}$การหลบหลีกชั้นที่สองที่ไม่สนใจค่า Hit ของผู้โจมตี ถือเป็นตาข่ายนิรภัยสำหรับสาย LUK สูง ลำดับความสำคัญในการคำนวณ (Calculation Order and Tagging)สถาปัตยกรรมทางคณิตศาสตร์นี้มีความเสี่ยงสูงที่จะพังทลายในช่วงท้ายเกมหากไม่มีการควบคุมลำดับการคิดคำนวณ ตัวเกมจึงบังคับใช้กฎ "Additional Value" ซึ่งกำหนดลำดับความสำคัญไว้อย่างเข้มงวด ได้แก่ Base (ค่าพื้นฐาน) $\rightarrow$ Flat Bonus (โบนัสคงที่) $\rightarrow$ Percentage Multiplier (ตัวคูณเปอร์เซ็นต์) สมมติฐาน: หากตัวละครมีค่าพลังชีวิตพื้นฐานที่ 1,000 สวมชุดเกราะที่บวก Flat HP +500 และบัฟสกิลที่บวก HP +20% ระบบจะนำ (1,000 + 500) = 1,500 จากนั้นจึงคูณ 20% ผลลัพธ์คือ 1,800 หากระบบคูณเปอร์เซ็นต์ก่อน ผลลัพธ์จะเป็นเพียง 1,700 การบังคับใช้ตรรกะนี้ทำให้ผู้เล่นต้องจัดสรรอุปกรณ์ทั้งสองประเภทอย่างสมดุล  นอกจากนี้ ตัวดัดแปลง (Modifiers) ทั้งหมดจะถูกจัดการด้วยระบบ Tagging เช่น แท็ก "Passive" หรือ "Temporary Buff" ทำให้โปรแกรมสามารถดึงค่าออกหรือคำนวณใหม่ได้อย่างรวดเร็วเมื่อบัฟหมดเวลา โดยไม่ต้องโหลดโปรไฟล์ของตัวละครใหม่ทั้งหมด 4. โครงสร้างคลาสอาชีพและการทำงานร่วมกัน (Class Archetypes & Synergies)ความลึกซึ้งของระบบ Attribute นำไปสู่ความหลากหลายของคลาสผู้เล่น โครงการนี้กำหนดแนวทางสายอาชีพหลัก 12 สาย แบ่งออกเป็น 4 บทบาททางยุทธวิธีหลัก แต่ใช้เศรษฐศาสตร์ของการกระทำที่ผู้เล่นสามารถควบคุมและจัดการได้ผ่านค่าสถานะ  ทักษะ (Skills) ถูกแบ่งเป็นสามประเภทหลัก: Active (เรียกใช้โดยตรงและกินทรัพยากร), Toggle และ INT (ความรวดเร็วในการประมวลผลทางจิต) Fixed Cast Time (FCT): ระยะเวลาหน่วงคงที่ที่ "ไม่สามารถลดทอนได้" ด้วยค่าสถานะปกติ ทักษะทำลายล้างสูงมักจะมี FCT ที่ยาวนาน เพื่อป้องกันไม่ให้ผู้เล่นในช่วงท้ายเกมสแปมสกิลหมู่ทำลายสมดุลของเกม Cast Delay: ระบบคูลดาวน์ระดับโลก (Global Cooldown) ที่ส่งผลต่อ ทุกทักษะ หลังจากที่ตัวละครออกท่าทางเสร็จสิ้น เป็นการจำกัดจำนวนการกระทำต่อวินาทีโดยรวม Cooldown: คูลดาวน์เฉพาะเจาะจงของทักษะนั้นๆ ป้องกันการใช้ทักษะเดิมซ้ำๆ แม้ว่า Cast Delay จะสิ้นสุดลงแล้วก็ตาม การออกแบบที่แยกส่วนกันนี้เปิดโอกาสให้ทีมออกแบบสร้างโปรไฟล์ทักษะที่หลากหลาย เช่น เวทมนตร์โจมตีระดับต่ำอาจมี VCT สูง (แต่ลดได้) FCT เป็นศูนย์ และไม่มี Cooldown ทำให้เป็นสกิลหลัก (Spammable) สำหรับช่วงท้ายเกม ในขณะที่เวทมนตร์อุกกาบาตอาจมี FCT 3 วินาที และ Cooldown 30 วินาที บังคับให้ผู้เล่นต้องคำนวณจังหวะอย่างรอบคอบ นอกจากนี้ การขยายผลของทักษะ (Skill Scaling) ไม่ได้ยึดติดอยู่กับ ATK ทิศทางนี้สอดคล้องอย่างสมบูรณ์กับกลไก "วงล้อเวลา 24 ชั่วโมง"  ของเกม การใช้แสงไฟไดนามิก (Dynamic Lighting) รังสีสะท้อน (Parallax) และเอฟเฟกต์หมอกเชิงปริมาตร จะทำให้ช่วงเวลากลางคืนที่มีมอนสเตอร์เก่งขึ้น ดูน่าสะพรึงกลัวและสมจริง  HD-2D ไม่ใช่เพียงความสวยงาม แต่เป็นเครื่องมือในการเล่าเรื่องทางยุทธวิธีของเกม9. สถาปัตยกรรมอินเทอร์เฟซและประสบการณ์ผู้ใช้ (UI/UX Architecture for Complex Systems)ด้วยความซับซ้อนของค่าสเตตัสหลัก 6 ตัว สูตรคำนวณสเตตัสรองอีกนับสิบ และกลไกอุปกรณ์ การออกแบบ User Interface (UI) และ User Experience (UX) ถือเป็นจุดชี้เป็นชี้ตาย (Make or break) ของเกม  แอปพลิเคชันเชิงลึกหรือเกม RPG ขนาดใหญ่ต้องถูกออกแบบมาเพื่อรองรับผู้เล่นระดับเชี่ยวชาญ (Expert Users) ในขณะที่ไม่ผลักไสผู้เล่นหน้าใหม่ หลักการเปิดเผยข้อมูลแบบค่อยเป็นค่อยไป (Progressive Disclosure)อินเทอร์เฟซไม่ควรโยนข้อมูลคณิตศาสตร์ทั้งหมดใส่หน้าจอผู้เล่นในครั้งเดียว แต่ควรใช้สถาปัตยกรรมการเปิดเผยข้อมูลตามบริบท หน้าจอแสดงอาวุธและสเตตัส (Weapon Stat UI): แทนที่จะออกแบบหน้าจอแบบตารางรกๆ หน้าจอรายละเอียดไอเทมจะถูกจัดเรียงใหม่ให้มีความเป็นระเบียบ (Clean and functional) โดยไฮไลต์เฉพาะค่าสถานะหลัก (Damage, Accuracy, Fire Rate) ไว้ในระดับสายตาแรก  เมื่อผู้เล่นนำเมาส์ไปวางทับ (Hover) หรือกดดูรายละเอียดเพิ่มเติม Tooltip อัจฉริยะจะปรากฏขึ้นเพื่ออธิบายว่าค่า "Perfect Dodge" ถูกคำนวณมาจาก $\frac{LUK}{10}$ ช่วยให้ผู้เล่นเข้าใจคณิตศาสตร์เบื้องหลังเกมโดยไม่ต้องสลับออกไปอ่านวิกิพีเดียภายนอก ระบบแนะนำภายใน Skill Tree: แทนที่จะพึ่งพาข้อความบรรยายสกิลแบบยาวยืด ต้นไม้ทักษะควรรวมเอาระบบ "Video Tooltip" เอาไว้ภายใน เมื่อผู้เล่นเลือกดูโหนดสกิลใหญ่ๆ หน้าต่าง UI เล็กๆ จะเล่นวิดีโอสาธิตแอนิเมชันของสกิลนั้นแบบลูป  สิ่งนี้ช่วยตอบสนองต่อสุนทรียภาพทางจิตวิทยา และทำให้การเลือกเส้นทางบนต้นไม้ที่มีนับร้อยโหนดง่ายขึ้นและน่าพึงพอใจ 10. โครงสร้างทางเทคนิคและการจัดการการผลิต (Technical Architecture & Production Framework)เบื้องหลังงานภาพที่สวยงามและคณิตศาสตร์ที่ซับซ้อน โครงสร้างพื้นฐานทางเทคนิค (Backend Architecture) ต้องได้รับการออกแบบมาให้มีความยืดหยุ่น ยั่งยืน และสามารถขยายขอบเขตได้อย่างอิสระ (Scalable and Decoupled)  การเขียนโค้ดที่ผูกติดกัน (Monolithic Codebase) จะทำให้การแก้บั๊กในช่วงการผลิตเกิดหายนะอย่างหลีกเลี่ยงไม่ได้ข้อมูลที่ขับเคลื่อนด้วย ScriptableObjectsเอนจินของเกม (ซึ่งมีแนวโน้มที่จะสร้างบนเครื่องมือข้ามแพลตฟอร์มอย่าง Unity 2025 หรือ Unreal Engine 5.3+ ตามเทรนด์การผลิตสมัยใหม่ ) จะใช้รูปแบบโครงสร้างข้อมูลอย่าง ScriptableObjects เพื่อจัดการข้อมูลไอเทม ทักษะ และตัวละคร 
แนวทางนี้จะแยกข้อมูล (Data) ออกจากตรรกะเชิงพฤติกรรม (Logic) ตัวอย่างเช่น แทนที่โปรแกรมเมอร์จะต้องเขียนคลาสโค้ดเฉพาะสำหรับดาบไฟแต่ละเล่ม นักออกแบบเกม (Game Designer) สามารถสร้าง ItemData ใหม่ใน Editor ตั้งค่า VCT กำหนดตัวคูณ INT และกำหนดประเภทได้อย่างอิสระโดยไม่ต้องแตะโค้ด  สิ่งนี้เพิ่มความเร็วในการสร้างต้นแบบ (Rapid Prototyping) ในช่วงการพัฒนาอย่างก้าวกระโดด สถาปัตยกรรมที่ขับเคลื่อนด้วยเหตุการณ์ (Decoupled Event-Driven Architecture)การอัปเดตสถานะที่ซับซ้อนระหว่างคณิตศาสตร์ อินเทอร์เฟซ และเอฟเฟกต์ จะถูกดำเนินการผ่านโครงสร้าง Event ของ C# อย่างเต็มรูปแบบ (เช่น Observer Pattern) เมื่อผู้เล่นสวมใส่ถุงมือที่บวกโบนัสสเตตัส ระบบสิ่งของคงคลังจะไม่สั่งการอินเทอร์เฟซโดยตรง แต่จะตะโกนแจ้งเตือนผ่านเหตุการณ์ (Event) OnAttributesChanged ทั่วทั้งระบบ สคริปต์ Base Character ที่กำลังฟัง (Listen) เหตุการณ์นี้อยู่ จะคำนวณสมการ HP และ Flee ใหม่ทันทีระบบ UI ที่กำลังฟังอยู่เช่นกัน จะดึงข้อมูลค่าสถานะใหม่มาแสดงผล และทำการลากเส้นแถบพลังงานให้ขยับขึ้นอย่างนุ่มนวลในขณะต่อสู้ หากนักพัฒนาแก้ไขสูตรของ LUK ระบบ UI จะไม่มีทางพัง และตัวละครจะไม่เกิดบั๊กแอนิเมชันค้าง  ถือเป็นการออกแบบทางวิศวกรรมที่เสถียรที่สุดสำหรับโปรเจกต์ระดับนี้บทสรุปเชิงกลยุทธ์ (Strategic Conclusions)การพัฒนางานตามข้อมูล GDD ฉบับนี้ ชี้ให้เห็นถึงสถาปัตยกรรมเกม 2D RPG ที่มีความลึกซึ้งทางการวิเคราะห์และการคำนวณเหนือกว่ามาตรฐานทั่วไป โครงสร้างนี้ใช้ความโปร่งใสทางคณิตศาสตร์ในการสร้างแรงจูงใจให้ผู้เล่น โดยหลีกเลี่ยงข้อจำกัดแบบคลาสอาชีพดั้งเดิม มุ่งสู่การปรับแต่งได้อย่างอิสระ การนำเอกสารนี้ไปปรับใช้เพื่อให้เกมประสบความสำเร็จ ต้องยึดมั่นในหลักการสำคัญ 3 ประการ:ความสมบูรณ์แบบในการลำดับทางคณิตศาสตร์: ลำดับสมการ Additional Value (Base $\rightarrow$ Flat $\rightarrow$ Percentage) ต้องถูกฝังรากในเครื่องมือการคำนวณทุกส่วนของเกม เพื่อเป็นโครงสร้างพื้นฐานที่ป้องกันอัตราเงินเฟ้อทางสเตตัส (Stat Inflation) ทำให้มั่นใจว่าเกมเพลย์ช่วงทดลองและช่วงเอนด์เกมมีความเสถียรเท่าเทียมกันประสบการณ์ผู้ใช้เป็นตัวเชื่อมต่อทางจิตวิทยา: ด้วยระบบที่มีการเชื่อมโยงความสัมพันธ์ของค่าสเตตัสหลัก 6 ตัวไปยังสเตตัสการต่อสู้ 8 ตัว การทำ UI ด้วยกระบวนทัศน์การเปิดเผยข้อมูลตามบริบท (Progressive Disclosure) และมี Feedback ทางภาพที่แข็งแกร่ง ScriptableObjects และโครงสร้างกราฟิกแบบ HD-2D จะช่วยให้ทีมสามารถรังสรรค์โลกที่มีพลวัตตามวัฏจักร 24 ชั่วโมง โดยมีต้นทุนการดูแลโค้ดที่ต่ำ และต่อยอดระบบคลาสทั้ง 12 REALM OF HERO: Whispers of the Pale Throne

Game Design Document — v0.1 (Draft) Single-player Action RPG • Top-down 2D • Mid-core

1. Game Overview

1.1 Concept Statement

"Realm of Hero: Whispers of the Pale Throne" เป็นเกม Action RPG มุมมอง Top-down ที่ผู้เล่นรับบทเป็น "Noname" นักเดินทางไร้นามในโลกหลังการล่มสลายที่ต้องเอาตัวรอดท่ามกลางสงครามตัวแทนของเทพบรรพกาลและเทพนอกจักรวาล โดยที่ผู้เล่นอาจเป็นเพียงพยานผู้บันทึกเหตุการณ์หรือตัวแปรสำคัญที่เปลี่ยนผลลัพธ์ของบัลลังก์ซีดจาง

1.2 Key Pillars

Reactive Combat: ระบบต่อสู้ที่เน้นจังหวะ การใช้ธาตุ และการแก้ทางศัตรูตามขนาดและประเภท

Deep Progression: ระบบ Stat 6 สายหลัก (STR, AGI, VIT, INT, DEX, LUK) พร้อม Class 12 รูปแบบที่ส่งผลต่อรูปแบบการเล่นเชิงลึก

Meaningful Choices: การเลือก Faction และความสัมพันธ์กับตัวเอก (Serina, Alveros, Hymera) จะกำหนดตอนจบของโลก

World Atmosphere: บรรยากาศโลกที่หนาวเหน็บและบิดเบี้ยวด้วยระบบกลางวัน-กลางคืน และ Shadow Zones

Shadow Hunters: นักล่าที่ใช้พลังเงาเพื่อความแข็งแกร่ง (สาย Shadow/Agility)

Cult of the Stars: ผู้ศรัทธาในเทพนอกดารา ยอมรับการกลายพันธุ์ (สาย Corruption/Magic)

Ancient Wanderers: กลุ่ม Noname เป็นกลางที่เน้นการค้าและข้อมูล (สาย Utility/Trade)

3. Core Gameplay Loop

3.1 Macro Loop

Explore: ออกสำรวจจากอาร์เวลเข้าสู่เขตเงาเพื่อหาทรัพยากร

Combat: ต่อสู้กับสัตว์ประหลาดและเทพนอกดาราเพื่อรับ EXP และ Loot

Progress: นำเศษพันธสัญญา (Covenant Shards) กลับมาอัปเกรดตัวละคร

Build: ปรับแต่ง Stat และ Skill Tree ตามสาย Class ที่เลือก

Decide: เลือกข้างในเหตุการณ์สำคัญระหว่าง Serina และ Alveros

3.2 System Stat & Combat

Core Stats: STR (Atk/Weight), AGI (Flee/ASPD), VIT (HP/Def), INT (Matk/VCT), DEX (Hit/VCT), LUK (Crit/Status)

Casting System: * Variable Cast Time (VCT): ลดลงตามค่า DEX และ INT

Fixed Cast Time (FCT): ลดลงตามคุณสมบัติของไอเทมพิเศษเท่านั้น

Shadow Calling: ระบบเรียกวิญญาณมาช่วยสู้ชั่วขณะ (ใช้ Shadow Stones เป็นทรัพยากร)

4. Power System & Mechanics

4.1 Cosmic Corruption (ความแปดเปื้อน)

การใช้พลังจากเทพนอกดาราหรืออยู่ในเขตม่านจักรวาลนานเกินไปจะเพิ่มค่า Corruption:

25-50%: เพิ่มพลังโจมตีแต่ลด Max HP

75% ขึ้นไป: มนุษย์ในเมืองจะหวาดกลัวและไม่ค้าขายด้วย

100%: Lost (Game Over หรือกลายเป็นศัตรู)

4.2 Shadow Taint

การอัญเชิญเงาโบราณบ่อยครั้งจะทิ้งรอยประทับไว้ในวิญญาณ ทำให้ร่างกายทนทานต่อความเย็นแต่จะถูกตามล่าโดยอัศวินวิญญาณของเอเธรานิลได้ง่ายขึ้น

5. Story & Endings

5.1 โครงสร้างบท

Prologue: การมาถึงของ Noname และการพบเห็นการตื่นของ Serina

Chapter 1-3: การออกล่าเศษพันธสัญญาและการเผชิญหน้ากับอัศวินอัลเวรอส

Final Chapter: การตัดสินใจ ณ บัลลังก์ซีดจาง

5.2 Multiple Endings

Ending A (Order): ช่วยอัลเวรอสฟื้นฟูพันธสัญญาเดิม โลกกลับสู่ระเบียบแต่ขาดอิสรภาพ

Ending B (Ruin): สนับสนุนเซรินาทำลายพันธสัญญาโดยสมบูรณ์ มนุษย์เป็นอิสระท่ามกลางโลกที่อันตราย

Ending C (Ascension): ยอมรับพลังเทพนอกดาราและกลายเป็นภาชนะใหม่ให้สิ่งมีชีวิตต่างมิติ

Ending D (The Witness): ไม่เลือกข้างและรอดชีวิตไปพร้อมกับบันทึกประวัติศาสตร์ในฐานะ Noname

6. Development Roadmap

Phase 1: พัฒนาตัวต้นแบบระบบ Combat และการคำนวณ Stat

Phase 2: สร้างแผนที่หมู่บ้านอาร์เวลและศาลเจ้าเงาแห่งแรก

Phase 3: วางระบบ Faction และ Dialogue Tree

Phase 4: ช่วงทดสอบสมดุล (Balancing) ของ Class ทั้ง 12 สาย

Phase 5: ปล่อยตัวเกมฉบับสมบูรณ์พร้อมตอนจบทุกรูปแบบ
